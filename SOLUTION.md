# Решение: симулятор Train Ticket на интерпретаторе Java

Запуск (только стандартная библиотека Python 3.8+, ~1 с на все сценарии):

```bash
python3 your_solution.py skeleton/trainticket.json.gz targets/trainticket scenarios/*.json -o submission.json
python3 platform/evaluate_golden.py gold/S0.json submission.json      # S0: 1.000
python3 your_solution.py ... -v                                       # журнал запросов, предупреждений, неопределённых условий
```

## Идея

Балл за сценарий — IoU по четырём множествам рёбер, и «даже с идеальными входами» статическое замыкание по скелету
даёт 0,5–0,76, потому что не знает ветвлений. Поэтому решение **не обходит граф, а исполняет код**: оно читает Java-исходники
проекта и «прогоняет» сценарий через интерпретатор Java с БД в памяти, записывая, какие методы, вызовы, межсервисные
запросы и обращения к таблицам реально произошли. Условия (`if`, циклы, исключения) вычисляются по настоящим значениям:
по телу запроса, по состоянию БД из `context/db-after-warmup.sql.gz` и по результатам предыдущих шагов.

```
шаги сценария (текст) ──► scenario.py: клиент-эмулятор UI ──► HTTP-запрос к шлюзу
                                                              │ маршрутизация по @RequestMapping
                                                              ▼
                       web.py ──► interp.py: интерпретатор Java ◄── model.py (AST + типы + скелет)
                          ▲            │  вызовы библиотек ─► lib.py (JDK/Spring/Jackson)
   RestTemplate между сервисами ◄──────┤  репозитории ─────► repo.py (Spring Data + Hibernate-семантика) ─► db.py (дамп)
                                       ▼
                               Trace: executes / calls / remote / data  ─► submission.json
```

| Модуль | Что делает |
| --- | --- |
| `jparse.py` | Токенизатор и парсер Java 8 (классы, обобщения, лямбды, анонимные классы). Позиции вызовов совпадают с `call_site` скелета (8952 из 8961) |
| `model.py` | Классы, поля, методы, разрешение имён типов (импорты, пакеты, вложенные классы); привязка методов AST к ID скелета по `(файл, строка)` — 1492 из 1492 |
| `interp.py` | Интерпретатор: выражения, операторы, конструкторы, виртуальная диспетчеризация, исключения, бины Spring (`@Autowired`), значения `UNK` для невычислимого |
| `lib.py` | Нужное проекту подмножество JDK: коллекции, `String`, `Optional`, `BigDecimal`, `Calendar`/`Date`, потоки, `ResponseEntity`… |
| `repo.py` | Spring Data: производные запросы по имени метода, `@Query`, `save/delete`, таблицы коллекций (`@ElementCollection`), ленивая загрузка, кэш сессии |
| `web.py` | Маршрутизация запросов к контроллерам, `RestTemplate` между сервисами, JSON-преобразования Jackson, `AuthenticationManager`, RabbitMQ |
| `scenario.py` | Шаг на английском → HTTP-запрос (как делает веб-интерфейс), состояние клиента между шагами (токен, найденные рейсы, контакт, заказы) |
| `solve.py` | CLI: свежая копия БД на каждый сценарий, сбор рёбер, проверка ID по скелету |
| `config.py` | Переключатель гипотез разметки (`TRACE_CLIENT_JSON`) |
| `tools/` | Отладка: `flow.py` (дерево исполнения шага), `dbdiff.py` (изменения БД), `failing.py` (внутренние ответы `status=0`), `sens.py` (вклад шагов), `fuzz.py` (прогон всех 262 обработчиков) |

## Как модель устроена и почему она точна

* **Скелет и исходники** используются совместно: скелет — источник точных ID методов и таблиц; AST — управляющая структура.
* **Состояние**: БД из дампа (≈200 строк), даты (`now = 15.09.2026`), результаты прошлых шагов. Заказ, созданный шагом 6, виден шагу 7 и т. д.
* **Правила разметки эталона**, выведенные из S0 и учтённые в трассировке:
  * исполнившимся считается метод, в теле которого есть операторы (пустые конструкторы и методы не попадают);
  * методы проекта, вызванные Jackson (разбор тела запроса, сериализация ответа), в эталон не попадают, а вызванные
    Hibernate (конструктор сущности при загрузке строк), Spring Security (`User#getAuthorities`…), `Logger`/`toString` и
    `ArrayList.contains → equals` — попадают как `executes` без ребра `calls`;
  * `JWTFilter#doFilterInternal` исполняется при каждом входящем HTTP-запросе, его вызовы `JWTUtil` не учитываются;
  * ребро `data` приписывается методу, где стоит вызов репозитория; SQL отложенной загрузки коллекции — ближайшему не-сущностному
    методу в стеке, `save` — методу с вызовом `save`; повторное чтение той же сущности в рамках одного запроса SQL не выполняет (кэш Hibernate);
  * (подтверждено диагностическими сдачами на платформе, `solution/tools/make_probes.py`, `predict.py`) рёбра `calls` **к**
    конструкторам не ставятся; конструктор попадает в `executes` только если сам вызывает методы проекта (`Order#<init>` → `OrderStatus#getCode`);
  * библиотечные обратные вызовы (`toString`, `equals`, Spring Security) дают ребро `calls` от ближайшего метода проекта, если в его исходнике есть
    вызов с тем же именем; через сгенерированные Lombok кадры ребро не ставится (`TravelResult#isStatus` — только `executes`);
  * конструктор, созданный Jackson при разборе тела запроса, попадает в эталон, если вызывает методы проекта
    (`RebookInfo#<init>` → `StringUtils#Date2String`); явные сеттеры/геттеры Jackson — нет (`config.JACKSON_CTORS_WITH_CALLS`);
  * SQL ленивой коллекции, которую читает Jackson при сериализации ответа (`route_stations`, `train_food_list` …), не приписывается никому;
  * тело запроса «расширенного поиска» (`travelPlan/cheapest|quickest|minStation`) несёт дату без времени (`2026-10-01`): тогда запрос
    мест к order-service находит заказы D1345/G9998 на эту дату и `OrderServiceImpl#getSoldTickets` вызывает `LeftTicketInfo#toString`
    (подтверждено сдачей r7: все сценарии 1.000);
  * `NullPointerException` из `StringUtils.String2Date(null)` при фильтрах заказов обрывает запрос (в эталоне S0 код «до ошибки» учтён).
* **Безопасность**: правила `configure(HttpSecurity)` каждого сервиса исполняются на «записывающем» билдере, токен несёт роли,
  запрос без подходящей роли получает 403 (на S0–S7 отказов нет — подтверждает, что цепочки допустимы).
* **Незнакомый шаг**: `scenario.py` выбирает обработчик по пересечению слов шага с именем метода/путём и вызывает его с типовыми аргументами.
* **Неопределённость** (`UNK`) не угадывается молча: она распространяется по выражениям, а условие над `UNK` решается
  эвристикой «исполнять ветку без ошибок» и попадает в журнал (`-v`). На S0–S7 таких условий не остаётся.

## Результаты

| Сценарий | executes | calls | remote | data | |
| --- | --- | --- | --- | --- | --- |
| S0 (эталон) | 34 / 34 | 24 / 24 | 0 / 0 | 7 / 7 | **1.000** (baseline_nlp: 0.431) |
| S1–S7 | 165–201 | 177–283 | 30–51 | 35–46 | эталонов нет; построены полные цепочки (оплата, возврат, перенос, отказ после получения билета…) |

Дополнительные проверки без эталона: сценарии воспроизводят свои собственные описания (оплата «с баланса» идёт внутри
сервиса, а у нового пользователя — через внешний платёж; возврат после получения билета отклоняется; пересадка и самый
дешёвый рейс находятся), а таблицы `consign_record`, `food_order`, `inside_money` после прогона совпадают по формулам
с тем, что оставила разминка (`2 кг → 12`, `возврат = 0,8·цена`).

## Ограничения и допущения

* Как именно тестовая обвязка превращает шаги в запросы, неизвестно; сопоставление шагов — по смыслу (`scenario.py`, таблица `RULES`).
  Малозначимые шаги («открыть заказ», «посмотреть цену») влияют на итог ≤ 1–2 %; решающие (вход, поиск, бронь, список заказов) однозначны.
* Подмножество JDK/Spring реализовано ровно в объёме, который нужен коду проекта; неподдержанный вызов даёт `UNK` и предупреждение.
* Запуск самого Train Ticket не требуется и не используется; рантайм-данные не собирались.
