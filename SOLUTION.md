# Решение: симулятор Train Ticket на интерпретаторе Java

Запуск (только стандартная библиотека Python, около 1–2 с на все сценарии):

```bash
python3 your_solution.py skeleton/trainticket.json.gz targets/trainticket scenarios/*.json -o submission.json
```

Синтаксис совместим с Python 3.8; запуск проверен на 3.12, 3.14 и 3.15 с одинаковым результатом.

## Идея

Балл за сценарий — IoU по четырём множествам рёбер, и «даже с идеальными входами» статическое замыкание по скелету
даёт 0,5–0,76, потому что не знает ветвлений. Поэтому решение **не обходит граф, а исполняет код**: оно читает
Java-исходники проекта и «прогоняет» сценарий через интерпретатор Java с базой в памяти, записывая, какие методы,
вызовы, межсервисные запросы и обращения к таблицам реально произошли. Условия (`if`, циклы, исключения) вычисляются
по настоящим значениям: по телу запроса, по состоянию базы из `context/db-after-warmup.sql.gz` и по результатам
предыдущих шагов.

```
шаги сценария (текст) ──► scenario.py: эмулятор веб-клиента ──► HTTP-запрос к шлюзу
                                                                 │ маршрутизация по @RequestMapping
                                                                 ▼
                       web.py ──► interp.py: интерпретатор Java ◄── model.py (AST, типы, скелет)
                          ▲            │  вызовы библиотек ─► lib.py (JDK, Spring, Jackson)
   RestTemplate между сервисами ◄──────┤  репозитории ─────► repo.py (Spring Data, Hibernate) ─► db.py (дамп)
                                       ▼
                               Trace: executes / calls / remote / data  ─► submission.json
```

## Структура

| Модуль | Что делает |
| --- | --- |
| `your_solution.py` | Точка входа из условия задачи |
| `solution/solve.py` | CLI: свежая копия базы на каждый сценарий, правила разметки, рёбра с ID из скелета |
| `solution/context.py` | Дата поездок, системное время и учётная запись из поля `context` скелета |
| `solution/scenario.py` | Шаг на английском → HTTP-запрос, как его отправляет веб-интерфейс; состояние клиента между шагами |
| `solution/web.py` | Обработчики `@RestController`, `RestTemplate` между сервисами, Jackson, Spring Security, RabbitMQ |
| `solution/interp.py` | Интерпретатор: выражения, операторы, конструкторы, виртуальная диспетчеризация, исключения, бины Spring |
| `solution/lib.py` | Нужное проекту подмножество JDK: коллекции, `String`, `Optional`, `BigDecimal`, даты, потоки |
| `solution/repo.py` | Spring Data: производные запросы, `save`/`delete`, таблицы коллекций, ленивая загрузка, кэш сессии |
| `solution/model.py` | Классы, поля, методы, разрешение имён типов; привязка методов к ID скелета |
| `solution/jparse.py` | Токенизатор и разборщик Java 8; позиции вызовов совпадают с `call_site` скелета |
| `solution/db.py` | Разбор дампа MySQL |
| `solution/values.py` | Значения времени выполнения (объекты, коллекции, исключения, `UNK`) |

## Правила разметки эталона

Выведены из S0 и подтверждены диагностическими сдачами (каждая гипотеза проверялась изменением одного сценария):

* исполнившимся считается метод, в теле которого есть операторы (пустые конструкторы и методы не попадают);
* методы проекта, вызванные Jackson (разбор тела запроса, сериализация ответа), в эталон не попадают, а вызванные
  Hibernate (конструктор сущности при загрузке строк), Spring Security (`User#getAuthorities`…), `Logger`/`toString`
  и `ArrayList.contains → equals` попадают как `executes`;
* библиотечный обратный вызов даёт ребро `calls` от ближайшего метода проекта, если в его исходнике есть вызов с тем
  же именем (`getToken → User#getPassword`); через сгенерированные Lombok кадры ребро не ставится;
* рёбра `calls` **к** конструкторам не ставятся; конструктор попадает в `executes`, только если сам вызывает методы
  проекта (`Order#<init>` → `OrderStatus#getCode`); конструктор, созданный Jackson при разборе тела запроса, —
  тоже (`RebookInfo#<init>` → `StringUtils#Date2String`);
* `JWTFilter#doFilterInternal` исполняется при каждом входящем запросе, его вызовы `JWTUtil` не учитываются;
* ребро `data` приписывается методу с вызовом репозитория; SQL ленивой коллекции — ближайшему методу вне сущностей;
  SQL коллекции, которую читает Jackson при сериализации ответа, не приписывается никому; повторное чтение той же
  сущности в рамках запроса SQL не выполняет (кэш Hibernate);
* `NullPointerException` из `StringUtils.String2Date(null)` обрывает запрос, код «до ошибки» учитывается;
* тело «расширенного поиска» несёт дату без времени: тогда запрос мест к order-service находит заказы на эту дату.

## Обобщение на новые сценарии

Код писался под любой сценарий, а не под S0–S7:

* дата поездок, системное время и учётная запись берутся из `context` скелета, а не из кода;
* эмулятор клиента понимает основные действия веб-интерфейса: поиск (обычный, расширенный, с пересадкой),
  бронирование с едой, страховкой и багажом, оплату, получение билета, вход на станцию, возврат, отмену,
  переоформление с доплатой разницы, а также админ-консоль — список, добавление, изменение и удаление станций,
  типов поездов, тарифов, настроек, контактов, пользователей, маршрутов, рейсов и заказов (объект находится по имени
  из текста шага или по созданному ранее);
* неверный пароль даёт отказ во входе: сверка пароля эмулирует Spring Security;
* незнакомый шаг сопоставляется с обработчиком по словам; переменные пути и тело запроса заполняются из состояния
  клиента;
* каждый шаг получает собственный предел вызовов: зацикливание одного шага не обрывает остальные;
* UUID и случайные числа детерминированы и не зависят от порядка сценариев: ответ на сценарий одинаков при запуске
  отдельно и в наборе.

## Ограничения и допущения

* Как именно тестовая обвязка превращает шаги в запросы, неизвестно; сопоставление шагов — по смыслу
  (`scenario.py`, таблица `RULES`, запасной подбор по словам).
* Подмножество JDK и Spring реализовано в объёме, нужном коду проекта; неподдержанный вызов даёт `UNK` и
  предупреждение в журнале.
* Запуск самого Train Ticket не требуется и не используется; рантайм-данные не собирались.
