# TechArena: Semantic Graph Analysis — Solution Brief

## Задача
Предсказать граф исполнения микросервисного приложения Train Ticket для заданных пользовательских сценариев **без запуска приложения**.

На входе:
- `skeleton/trainticket.json.gz` — статический граф: методы, возможные вызовы, таблицы
- `scenarios/S0–S7.json` — описания действий пользователя на английском
- `context/db-after-warmup.sql.gz` — исходное состояние БД перед каждым сценарием
- `targets/trainticket/` — исходный код проекта (41 Java-сервис)

На выходе: JSON с четырьмя типами связей для каждого сценария:
```json
{
  "project": "trainticket",
  "scenarios": {
    "S0": {
      "edges": [
        {"source": "scenario:S0", "relation": "executes", "target": "method:..."},
        {"source": "method:A", "relation": "calls", "target": "method:B"},
        {"source": "method:A", "relation": "remote", "target": "method:B"},
        {"source": "method:A", "relation": "data", "target": "res:table:..."}
      ]
    }
  }
}
```

## Типы связей

| Связь | Определение | Когда добавлять |
|-------|-------------|-----------------|
| **executes** | сценарий → метод | Метод проекта выполнился хотя бы один раз |
| **calls** | метод → метод | Первый вызвал второй (в том числе через интерфейсы — указать реализацию) |
| **remote** | метод A → метод B (другой сервис) | Из одного сервиса ушёл HTTP-запрос/сообщение, обработал другой |
| **data** | метод → таблица | Из метода выполнился SQL к таблице (источник — где стоит вызов репозитория) |

## Ключевые правила

### Что включать:
- Методы **проекта** (не библиотеки: Spring, Hibernate, Jackson)
- **Все таблицы**, к которым ушёл SQL (включая коллекции: `user_roles`, `route_stations`)
- Операторы (`stmt:`) для методов, которые выполнились
- Вызовы через интерфейсы → реализацию, которая **действительно выполнилась**
- SQL, который ORM отложит до конца транзакции

### Что исключать:
- Автогенерированные методы Lombok
- Геттеры, вызванные библиотекой через отражение
- Вызовы Spring Framework как `calls` между двумя методами проекта
- `JWTFilter` как `calls` к обработчику (Spring запускает его, не фильтр)

### Порядок и дубликаты
- Множество: порядок не важен, дубликаты игнорируются
- Один сценарий = один граф (все шаги интегрированы)
- Если ошибка — код до ошибки всё равно считается

## Исходное состояние

Все сценарии начинаются с одинакового состояния:
- **БД**: `context/db-after-warmup.sql.gz` (одна разминка, затем восстанавливается перед каждым)
- **Пользователь**: `fdse_microservice` / `111111` (баланс 10,000, один контакт)
- **Дата**: 1 октября 2026 (сейчас 15 сентября)
- **Выбор**: "первый" означает первый в порядке системы (проверено — выбор другого не меняет методы)

Сценарии **не наследуют** состояние друг друга.

## Оценка

**IoU (Jaccard Index)** для каждого типа связи в каждом сценарии:
```
балл = |Ваши ∩ Эталон| / |Ваши ∪ Эталон|
```

Примеры:
- Вы добавили 3 ребра, в эталоне 4, совпали 2: `2 / (3+4-2) = 0.4`
- Оба пусты: `1.0`
- Эталон пуст, вы добавили хоть одно: `0.0`

**Итоговый балл**:
1. Среднее по 4 типам связей для каждого сценария
2. Среднее по 7 скрытым сценариям (S0 используется только для разработки)
3. **Бонус за Rust**: результат × 1.1 (но не более 1.0)

## Архитектура проекта

**Структура**: 41 Java-микросервис + веб-интерфейс + MySQL + RabbitMQ + Spring Cloud Gateway

**Ключевые сервисы**:
- `ts-auth-service` — аутентификация, токены
- `ts-order-service`, `ts-order-other-service` — заказы высокоскоростных и обычных поездов
- `ts-user-service` — профили, контакты
- `ts-assurance-service` — страховка
- `ts-consign-service` — багаж
- Другие специализированные сервисы

**Особенности**:
- Gateway маршрутизирует запросы по имени сервиса
- Общий код в `ts-common` входит в несколько deployment units
- ORM (Hibernate) может отложить SQL до конца транзакции
- RabbitMQ для асинхронных операций

## Что показали примеры решений

| Решение | Подход | Результат на S0 | На скрытых |
|---------|--------|-----------------|-----------|
| **baseline_bm25** | BM25 по тексту методов | 0.431 | ~0.09–0.13 |
| **baseline_closure** | Входы по путям + статическое замыкание | N/A | ~0.50 |
| **baseline_nlp** | UI-анализ + BM25 по коду+UI + замыкание | 0.431 | ~0.50 |

**Главный вывод**: даже с **идеальными входами** балл только ~0.52–0.76, потому что нужно учитывать:

1. **Условия в коде** — `if (status == PAID)` → разные ветки
2. **Состояние БД** — наличие заказов, контактов → разные пути
3. **Последовательность шагов** — результат шага N влияет на шаг N+1
4. **Циклы** — повтор/пропуск кода
5. **Исключения** — ошибки прерывают исполнение

## Как использовать скелет

**Узлы (nodes)**:
- `kind`: `method`, `call_site`, `module`, `type`, `field`, `data_resource` (таблица), `config_entry`
- ID начинается с префикса: `method:`, `call:`, `res:table:`, `cfg:` и т.д.
- **Берите полный ID целиком** из скелета — сокращения не принимаются

**Рёбра для навигации**:
- `calls` — место вызова → возможный метод (преобразовать: вызывающий метод → реальный метод)
- `runtime_dispatch` — интерфейс → реализация
- `remote_call`, `message_delivery` — переход между сервисами
- `data_access` — место → таблица
- `overrides` — для нахождения реализаций интерфейсов (CHA)
- Структурные рёбра (`contains`, `extends`, `implements`) помогают, но **не входят в ответ**

**Пример преобразования**:
```
Скелет: call:method:ts-order-service:Order#queryOrders@68:32 
        --calls--> method:ts-order-service:OrderService#query(...)

Ответ: method:ts-order-service:Order#queryOrders(...) 
       --calls--> method:ts-order-service:OrderService#query(...)
```

## Стратегия решения

### Фаза 1: Точка входа
1. Распарсить сценарий на естественный язык
2. Матчить с обработчиками (@RequestMapping, @GetMapping…)
3. Использовать UI-контекст из фронтенда для уточнения

### Фаза 2: Статический анализ
1. Загрузить скелет и исходный код
2. Для каждого метода: прочитать тело, найти условия
3. Построить CFG (control flow graph) — найти условные переходы

### Фаза 3: Трассировка
1. Симулировать исполнение с учётом начального состояния
2. Для каждого условия (`if`, `switch`) — предсказать ветку по контексту
3. Идти по `calls`, `remote_call`, `data_access` в скелете
4. Отслеживать состояние переменных между шагами

### Фаза 4: Таблицы БД
1. Найти все вызовы репозитория в выполненных методах
2. По `data_access` в скелете — найти таблицы
3. Учесть ORM-отложения
